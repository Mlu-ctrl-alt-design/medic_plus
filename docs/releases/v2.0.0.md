# medic_plus v2.0.0

**Release date:** 2026-05-08
**Phase boundary:** Phase 1 (SA EMR core) close — PRD #23, issue #28

This is the first major version of medic_plus. It rolls up Phase 1A–1E (the South-African EMR compliance core), Phase 4 (telemedicine + AI augmentation), POPIA controls, and a read-only FHIR R4 server. Sixteen commits, fifteen new doctypes, ~11k lines added.

## Headline changes

### South-African EMR compliance — Phase 1 complete

medic_plus now meets the structural requirements for a HPCSA-aligned electronic medical record:

- **Structured SOAP encounter (Phase 1C)** — encounter drawer captures Subjective / Objective / Assessment / Plan with Examination Findings child table and a Patient Problem List linked to ICD-10-ZA.
- **Drug Master + safety checks (Phase 1D)** — local Drug Master doctype, allergy / interaction / paediatric-dose checks, HPCSA Booklet 8 prescription print format with override-reason tracking.
- **Insurance Claims (Phase 1E)** — Insurance Claim + Tariff Code + Switch Configuration doctypes, claim builder, HealthBridge submission client, on-submit hook, cross-tenant PQCs.

### Phase 4 — Telemedicine + AI augmentation

- New `Telemedicine Consent` doctype + per-encounter teleconsult page at `/teleconsult`.
- `Practice AI Settings` + `AI Inference Log` for opt-in clinical AI usage; PHI redactor strips identifiers before any external call.
- AI gateway is provider-agnostic so a practice can choose its own model endpoint.

### POPIA controls

- `Patient Consent Record` + `Sub-Processor Register` doctypes seeded with at least 10 sub-processors (incl. HealthBridge).
- Daily scheduler `flag_expired_consent_records` marks Given consent records older than 3 years as Expired.
- Consent records and the sub-processor register are exposed via the patient drawer and platform admin views respectively.

### FHIR R4 read-only server

- Endpoint: `/api/fhir/R4/<ResourceType>/<id>` returning `application/fhir+json`.
- Six R4 resources: Patient, Encounter, Condition, MedicationRequest, AllergyIntolerance, Observation (vitals — BP/weight/height with LOINC + UCUM).
- `$everything` Bundle for a single Patient.
- `CapabilityStatement` at `/api/fhir/R4/metadata` (allow_guest).
- SMART-on-FHIR style bearer tokens via new `FHIR Access Token` doctype — SHA-256 hashes only stored, 1-hour TTL, practice-bound, cross-tenant access denied.

## New doctypes (15)

| Doctype | Purpose |
|---|---|
| `Examination Finding` | Child of Patient Encounter — structured Objective findings |
| `Patient Problem List` | Long-term ICD-10-ZA problems per patient |
| `Drug Master` | Local drug catalogue (NAPPI + interactions + paediatric flags) |
| `Prescription Override Reason` | Audit trail when a prescriber overrides a safety check |
| `Insurance Claim` + `Insurance Claim Line` | Claim header + line items, on-submit pushes to HealthBridge |
| `Tariff Code` | BHF/SAMA tariff catalogue |
| `Switch Configuration` | Per-practice claims switch credentials (HealthBridge first) |
| `Patient Consent Record` | POPIA-aligned consent capture; auto-expires after 3 years |
| `Sub-Processor Register` | Public-facing list of every processor handling PHI on behalf of the platform |
| `Telemedicine Consent` | Per-encounter consent for teleconsult |
| `Practice AI Settings` | Per-practice opt-in for AI augmentation + provider config |
| `AI Inference Log` | Audit log of AI calls (redacted prompt + response hash) |
| `Medic Plus Settings` | Single doctype for platform-wide flags (e.g. AI globally disabled) |
| `FHIR Access Token` | SMART v2 bearer token, hashed |

## Tests

- Tracer integration tests for claims, drug safety, FHIR mappers, POPIA, telemedicine, encounter — all under `medic_plus/tests/`.
- Playwright UI suites: `test_soap_encounter_ui.py`, `test_prescription_panel_ui.py`, `test_claims_fhir_ui.py`, `test_telemedicine_ai.py`.
- Cross-tenant isolation is asserted in every PQC test.

## Upgrade notes

- Migration is non-destructive: new doctypes only, additive custom fields on `Patient Encounter` (`custom_claim_diagnosis_code`, `custom_claim_nappi_code`, etc.).
- `pyproject.toml` adds `fhir.resources` (R5 model library — used to validate R4 JSON shape) and HealthBridge client deps. CI/CD installs these via `bench setup requirements` during the deploy workflow.
- `retention.flag_overdue_records` and `retention.flag_expired_consent_records` schedulers are registered in `hooks.py` — both are idempotent and guarded with `frappe.db.table_exists()` so the first migrate run does not fail before the new tables exist.
- No fixture renames; existing `Practice` / `Practice Member` / appointment data unchanged.
- No site-config flags are required to enable the new features; AI augmentation is **off by default** per practice and must be opted in via `Practice AI Settings`.

## Behind a flag / opt-in

- AI augmentation: per-practice via `Practice AI Settings`; disabled at platform level by `Medic Plus Settings.ai_disabled`.
- FHIR write endpoints: not in this release. Read-only only. Write requires a validation layer (planned for v2.1.x).

## Deferred / known gaps

- FHIR search (`?patient=<id>`) — router has stubs; pagination + SQL safety review still to land.
- FHIR SMART `/.well-known/smart-configuration` discovery document.
- Advanced reports + medical-aid integrations beyond HealthBridge — Pro-plan roadmap.
- SMS/WhatsApp OTP for booking (Africa's Talking) — config deferred.
